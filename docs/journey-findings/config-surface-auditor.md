## [J6] P2 (FIXED `8caae2e6`→`b31aec05`→`8c1ff8ce` — CLOSED, live-verified on train #9) — two quick tomato-duration writes: the first write silently bounces back on every surface, config.json included

Evidence (my J10 repro, DB forensics; corroborates pomodoro journeyB5/B6): settings page, 专注时长 5 then 10 written ~2.3s apart. t+2.8–3.8s all surfaces = 10 ✓; **t+4.35s store/LS/UI/config.json ALL revert to 5**, and the DB blob reads `{tomatoTime:5, _savedAt:t+2.0}` — the pre-second-write snapshot, landing late; t+4.9s the second blob lands and 10 re-applies. The user sees their change flap back to the old value and (per pomodoro B6's later reads) the flap can settle on the stale value.

Root cause: the renderer's own debounced db.settingsState mirror (persist 2s + dbMirror 2s ≈ DB write 4s after the change) lands in the SAME DB channel the external-db-watch settings branch hot-applies for CLI coexistence. A stale mirror generation landing after a newer state has `_savedAt >` the watcher watermark, so the watcher treats OUR OWN mirror as a fresh external change, diffs it against its previous snapshot, and broadcasts `{tomatoTime:5}` back — the renderer hot-applies it (updateExternal → update action → config IPC), reverting everything. Not LS ping-pong: it is mirror-generation reordering consumed as an external write.

Fix (`8caae2e6` + v2 `b31aec05`, D1 preserved): dbMirror records the newest `_savedAt` this window queued per key (`isOwnMirrorStamp`); the watcher sends the origin stamp as a 2nd arg on `external-settings-changed`; main.js dispatches it to `settings/updateExternal` PACKED INSIDE the payload (`{patch, originSavedAt}`), which skips patches covered by our own watermark. Foreign stamps (CLI/LAN peer) are newer and still apply; no-origin callers (LAN-sync rows, DB restore) and aux windows (never mirror) are untouched. Tests: `tests/unit/store/j-audit-echo-suppression.test.mjs` (watermark semantics + apply/suppress matrix + the PACKED shape).

**Train-#6 lesson (v1 `8caae2e6` was inert — caught by the same-key B5 gate, as insisted):** Vuex `dispatch(type, payload, options)` DROPS a bare third argument — the origin stamp arrived at the action as `undefined`, so suppression never fired in the real app while the direct-call unit test (which bypasses dispatch) passed. Compounding it, the revert-echo's own persist re-queued a newer-stamped stale blob into dbMirror pendings, overwriting blob#2 before its timer flushed — the user's second write never reached the DB and the state settled on the stale value permanently. Live signature on train #6: 10,10,10 then 5 forever from +4.5s (16 samples, 8s). Two audit rules this bought: (1) the different-key pair is a BLIND gate — its echo revert targets the current value and is invisible even with the fix dead; only the same-key pair honestly proves suppression; (2) an action needing >1 argument must take them packed in the payload, never as a third dispatch arg.

**Train-#8 chapter (v2 `b31aec05` also inert — three-layer excavation):** v2 packed the payload correctly and the renderer chain was proven correct in isolation (live packed probe: foreign patch applies, sub-watermark stamp suppresses). Yet the same-key bounce persisted with the identical +4.5s signature. Elimination: A/C/D pairs proven structurally blind (sub-debounce pairs coalesce into ONE mirror generation — no stale blob can exist); aux-window theory dead (storage-event counter stayed 0 through the bounce). The decisive instrument was a live `store.dispatch` monkey-patch logging every `updateExternal` payload: the revert arrived PACKED, origin `…6477`, while the blob's own stamp was `…4461` — **the watcher was sending `at` (= max(blob._savedAt, settingsRowsMaxUpdated)) as the origin, and settings_rows get re-stamped when our own mirror blob lands (~2s after its snapshot), so `at` always exceeded the renderer's watermark: every own-echo was foreign by construction.** v3 `8c1ff8ce`: origin = `doc._savedAt` (decision/absorb semantics unchanged); regression pins forbid the folded watermark as origin. Third audit rule: when a guard compares stamps ACROSS a boundary, the sender must send the same stamp class the receiver tracks — folding in a second, differently-stamped source (`settings_rows`) poisons the comparison while every unit test on either side stays green.

**Pre-existing gate red (not mine):** `cli/check-dualwrite.cjs` fails on HEAD for `TomatoFloatPage.vue::tomatoFloatVisPing:300` — LS write point landed unregistered with pomodoro's `0a7a0766`; needs the tomato owner's ledger registration.

**CLOSED on train #9 (18:29:33, `8c1ff8ce` aboard) — the honest gate green:** same-key 专注 5→10 @2.5s → **16/16 samples at 10 through +8s, zero reverts, config.json holds 10** (`45-j11-seqB.png`: the bottom-bar timer itself reads 10:00, the live tomato surface included). A/C/D also green for the record. Why this three-layer story is the reference for "why the honest gate matters":
- **Layer 1 — dispatch-signature bypass (v1):** the fix's unit test called the action DIRECTLY (`actions.updateExternal(ctx, …)`), bypassing `store.dispatch` — so the Vuex 3-arg drop that made the fix inert in-app was invisible to a 100%-green suite.

Only the same-key, past-debounce pair exercises the defect. The gate that looked hardest was the only real one.
