# PickDone 多设备同步 + 付费 · 整体技术方案

日期:2026-09-15 · 状态:P1 已落地(见文末路线图),本文为 P2 起的总规划
前置文档:《同步付费模式调研报告-2026-09-15.md》(商业模式与开源先例)

---

## 0. 一句话总纲

**端上存事实,云端只当哑保险箱,一切日程计算留在设备本地**;服务器=薄账号(Workers+D1)+加密 blob(R2),自托管单容器同协议;商业形态=思源模式(本地永久免费,托管同步收费,自托管免费出口)。

---

## 1. 设计原则(不可妥协项)

1. **本地优先不被稀释**:断网全功能、无账号可永久使用;服务器失联=暂时不能同步,不能是"不能工作"。
2. **端上存事实,云端不算日程**:服务器只存和转发事实行(todos/chips/账本/设置的变更),**提醒触发、重复任务展开、负载统计、番茄账本聚合全部在各设备端上计算**。服务器永远不做业务计算,才算得上"服务器读不懂也看不懂"。
3. **E2E 默认开**:上传前加密,服务器只见密文与元数据尺寸;密钥不上服务器。
4. **删除必须可传播**(P1 已完成墓碑化);GC 域(回收站清空/planPrune)靠快照对账,不进增量流。
5. **单写入口纪律**:一切变更必须过 `db.call()`(IPC/CLI/辅窗已保证),oplog 是唯一事实变更流;任何绕过 db 层的写入都是 P0 级架构破坏。

## 2. 总架构

```
┌─────────── 设备 A (Win/Mac/Linux) ───────────┐
│ Vue SFC renderer ──IPC──> main: db.call()     │
│                             ├─ SQLite(加密)   │
│                             ├─ sync_oplog(P1) │
│                             └─ SyncEngine(P2) │
│                                  │ 合并/加密   │
└──────────────────────────────────┼────────────┘
                        HTTPS(REST+长轮询/WS)
┌──────────────────────────────────▼────────────┐
│ Cloudflare Workers: /auth /devices /push /pull │
│   D1: 账号+设备表+游标(密文元数据)                │
│   R2: 每设备 oplog 分段 + 快照 + 附件(密文)      │
└──────────────────────────────────┬────────────┘
                    同一协议,自托管 = 单容器(Node)+任意S3
┌──────────────────────────────────▼────────────┐
│ 设备 B/C: 同一 SyncEngine(共享 JS 模块,见 §8) │
└───────────────────────────────────────────────┘
```

选型理由:R2 零出口流量费、D1 免费档够几千用户、Workers 无运维;数据量(todo 文本)极小,单用户全年增量 <10MB,免费/低价档成本可忽略。**拒绝**:Supabase(重、 vendor 锁)、自建 Postgres VPS(单人值班风险)、cr-sqlite(上游停滞,调研已排除)。

## 3. 服务器怎么搞

### 3.1 托管端(官方服务)

| 组件 | 选型 | 说明 |
|---|---|---|
| API | Cloudflare Workers(Hono/itty-router) | 5 个端点族,见 §3.3 |
| 账号库 | D1(SQLite) | users/devices/subscriptions 三表,存密码哈希(argon2id→Workers 需 WebCrypto PBKDF2 替代) |
| 数据 blob | R2 | 桶内路径 `/{userId}/{deviceId}/{segment}`,内容全是密文 |
| 限流 | Workers Rate Limiting | 防滥用推送 |
| 域名 | sync.pickdone.app(CF 同账号) | |

### 3.2 自托管端(免费出口)

单 Docker 容器:Node(与 CLI 同构复用 DB 层)+ 任意 S3 兼容存储(MinIO/坚果云 WebDAV 二期)。**协议文档化**(openapi + 协议规范.md),第三方可实现客户端——这是"自托管可信"的承诺,也是 Logseq 教训(闭源+停滞=信任崩)的反面。服务端 AGPL 开源,仓库独立(`pickdone-sync-server`),从第一天带 CLA。

### 3.3 API 面(最小集)

```
POST /auth/signup|login      → email+密码(PBKDF2),返回 refresh token
POST /auth/token             → 换短期 access token
POST /devices                → 注册设备(deviceId, 名称, 平台),返回 deviceSecret
POST /push   {segments[], cursor} → 上传本设备新 oplog 密文段
GET  /pull?since=            → 拉其他设备密文段索引+内容(长轮询可选 ?wait=25)
POST /snapshot               → 全量密文快照(GC 对账 + 新设备首同步)
GET  /snapshot/latest
POST /license/activate       → 激活码→订阅状态(离线宽限 30 天)
```

原则:**服务器不感知内容**,只做鉴权、配额(密文尺寸)、段序号单调性校验。多设备冲突的合并永远在端上。

## 4. 数据怎么搞(同步协议)

### 4.1 模型:oplog 增量 + 快照兜底

- **增量**:P1 的 `sync_oplog(seq, entity, entityId, ts)` 是本地事实源。SyncEngine 把"上次推完的 seq"以来的变更,按实体打包成**密文段**(每段 ≤256KB,含 `fromSeq..toSeq` 与行内容),push 上去。
- **游标**:本地持久化 `pushedSeq`(推到哪)与每远端设备的 `pulledSeq`(拉到哪);服务器 D1 存每设备 `lastSegmentSeq` 做单调校验。崩溃恢复语义沿用 commitSyncBatch 的经验:**推完才推进游标,推一半=整段重推**。
- **快照**:每 7 天或变更量 >5000 行自动做一次全量密文快照;新设备首同步直接下快照再补增量;GC 域(物理删)只在快照里对账。

### 4.2 冲突规则(确定性、可单测)

| 场景 | 规则 |
|---|---|
| 同一行两端都改(todos) | 字段级 LWW:比较行级 `updatedAt`,新者胜;输方内容进"冲突副本"(回收站可查,绝不静默丢) |
| 一端改一端删 | **删除胜**(墓碑 deletedAt > 行 updatedAt 时)。理由:todo 场景误删恢复走回收站,合并语义要简单到可解释 |
| 番茄账本 | **append-only 合并**:tomatoId 全局唯一,只增改不真删;两端同 id 取 focusDuration 大者(计费口径:宁可多记专注) |
| plan_chips | 行级 LWW + 墓碑;day 是纯字符串不参与计算,无时区问题 |
| 设置/habits(meta blob) | **P2 前置作业:拆行表**(照 plan_chips 行表化先例),blob 级 LWW 会互相整块覆盖,不可接受;拆完每键一行+updatedAt |
| 时钟偏差 | 排序一律用 **seq 序**(本机单调),`updatedAt` 只参与 LWW 比较;偏差 >5min 的设备在 UI 标警。拒绝用服务器时间戳裁决内容(服务器读不了明文) |

### 4.3 ID 与账号现状的处置

- 现状:userId 硬编码 840001 烤在存量 `tid_840001xxx_<ts>` 里;分类 id 是 Date.now() 种子整数,**跨设备创建必撞**。
- 方案:① 同步账号 uid 取代 840001(存量 ID 不改写,只在合并时视为"本机历史数据"整体并入);② 新分类/过滤器 id 改为 `Date.now()+随机+deviceId 哈希` 的 64bit 命名空间整数,向后兼容 INTEGER 主键;③ deviceId 由服务器注册时签发,本地生成临时 id 待激活时换正牌。

### 4.4 E2E 加密

- 密钥体系:主密钥 MK = PBKDF2(密码, 盐, 600k 迭代)→ 不上传;**包裹密钥 WK = 随机 256bit,真正加密数据**;WK 用 MK 包裹后存 D1(换密码只重包裹,不用重加密全库)。
- 算法:AES-256-GCM(WebCrypto 原生,Workers/Node/浏览器三端同构),每段独立 IV;段头含 schemaVersion+设备 id+seq 区间(明文,用于路由)。
- 忘记密码=数据不可恢复,注册页明示(与隐私卖点一致,写进文案)。

## 5. 日程的计算怎么搞(核心原则:facts vs views)

同步交换的是**事实**(任务行、芯片行、账本行),所有"日程视图与触发"都是**端上纯函数**:

| 计算项 | 位置 | 同步牵连与对策 |
|---|---|---|
| **提醒触发** | 各端 scheduler(现状:重启从 DB 重建一次性 setTimeout,已验证可靠) | 两端都会响=预期行为(手机+电脑同时提醒可接受 v1;后续加"任一端已读则他端静默"的已读墓碑) |
| **重复任务展开** | 端上按 recurGroupId+规则展开 | 规则行本身同步(现有 meta 重复规则→P2 随设置拆行表入行存储);**展开产物不落库不同步**,每端自己算,确定性由"规则+锚点日期"保证 |
| **scheduledDay(本地毫秒)** | 任务行字段 | ⚠️ 最大坑:它是"创建设备的本地日"。跨时区设备会把"今天"算歪。方案:**行上补 `tz` 字段**(IANA 名,P2 迁移), scheduledDay 语义不变,但他端展示时用 `tz` 换算;同任务两端编辑后以胜者行的 tz 为准 |
| **dateKey(账本日)** | 已由 endTime 单向重导(db 层强制) | 无冲突面,endTime 是绝对毫秒,天然跨时区正确 |
| **统计/负载/热力图** | 端上聚合(tomatoByDay 等现成 SQL) | 不同步任何统计结果;新设备首同步后重算即可 |
| **plan_chips 排程** | 端上按 day 字符串分桶 | day='YYYY-MM-DD' 纯日历日,无时区语义,直接同步 |

**判据**:任何"计算产物"如果不需要用户跨设备看到同一个值,就不同步。提醒响了两次可以接受,统计数字各端一致=靠重算而非靠传输。

## 6. 附件与多媒体(二期 P5)

现状:文件在 `userData/files/`,DB 只存 `local://` URL。方案:`local://` 旁加 `remote://<fileHash>`,SyncEngine 按 hash 上传密文对象到 R2(单文件 50MB 上限沿用现有 whitelist);下载按需+配额计量;免费档不含附件同步(付费差异点+成本护城河)。音频/内置资源永不同步。

## 7. 商业化接入(随 P4)

- 免费档:同步功能全开,**配额 25MB + 2 台设备**(v3 口径统一:免费档定位=体验档,墙落在容量增长与第二台设备的交叉点;附件不同步)。(v2 原文曾写 ≤100MB,已统一)
- 付费档:¥98-128/年 或 $30-40/年(不限设备、10GB、附件同步、90 天版本历史);限量创始 lifetime ¥399;续费锁价;明示"X GB 是我能负担的极限"。
- 激活:LemonSqueezy(海外 MoR)/ 爱发电·面包多(国内)→ 离线签名激活码,app 内验签,30 天联网宽限。**不建会员体系,不碰支付后台**,license 验签逻辑开源、私钥离线。
- UI:设置页"同步"分区(设备列表/游标状态/冲突副本入口/配额条),文案铁律:"本地功能永久免费"置顶。

## 8. 多端规划(哪些端、什么顺序)

同步引擎写成**平台无关 TS 模块**(`@pickdone/sync-core`:oplog 编解码/合并规则/加密/传输,零 Electron 依赖;db 层经适配器注入),这是多端快的前提,也是现有 SFC 同构架构的自然延伸。

| 端 | 顺序 | 复用面 | 判据(做下一个的门槛) |
|---|---|---|---|
| 桌面三平台 | 已有 | — | P1-P4 完成,双端互同步稳定 1 个月 |
| **Web(PWA)** | 第 2 端 | Vue SFC 全套 + browser shim(5175 宿主已验证)+ sync-core 直连 R2 | 桌面端付费转化数据确认需求;Web 天然是"第二台设备"最便宜形态 |
| **Android** | 第 3 端 | sync-core + SQLite;UI 用 Capacitor 包 Web 或 Compose 重写(拍板项) | Web 端留存 >30%;插件化提醒(android AlarmManager 需原生)是主要工作量 |
| iOS | 观望 | 同 Android | App Store 审核成本+E2E 应用政策;有付费用户基数再启 |

顺序依据:todo 用户"第二台设备"多数是手机,但 Web 开发成本是 Android 的 1/5,先用 Web 验证"多端同步值得付费"再投原生。

## 10. 风险与对策

1. **同步可靠性=支持负担**(Logseq 教训):P2 混沌测试投入占比全项目最高;发布前公开"同步协议规范"让社区可自证。
2. **免费墙设定失当**:25MB 体验档是 v3 统一口径——墙同时卡"第二台设备"与"容量增长"两个升级触发点;上线后按真实分布回调。
3. **Clock skew/时区坑**:tz 字段进 P2 迁移一次做对;scheduledDay 语义绝不改(存量数据兼容)。
4. **Workers 平台依赖**:协议+服务端双实现(官方 Workers/自托管 Node)互相校验,CF 锁不死我们。
5. **并行开发冲突**:sync-core 新目录+server 独立仓,避开 renderer store 高频改动区(category/habits/undo 有并行代理作业)。
