# 数据升级检查清单

每次改动持久化结构（DB schema / meta blob / config.json）后，发布前逐项过一遍。任何一项打不上勾，先补齐再发版。

## A. SQLite schema（todos 等表）

- [ ] 新列已同时加入 `SCHEMA`（建表语句）与 `MIGRATIONS`（迁移数组）——两处缺一会导致新库/旧库形状不一致（`pickdone/src/main/db.js`，schemaVersion 单迁移器）
- [ ] 加列使用 `PRAGMA table_info(...)` 幂等守卫（先查列是否存在再 `ALTER TABLE ... ADD COLUMN`），迁移重复执行不报错
- [ ] 新列带 `DEFAULT`，旧数据迁移后语义不变（NULL/0/空串行为已确认）
- [ ] `MIGRATIONS` 的 `v` 递增正确，迁移只跑一次（`schemaVersion` 落库）
- [ ] 迁移失败路径已想清楚：init 抛错会走 `dbRecovery` 分级恢复——确认恢复策略（备份恢复/降级）不会丢用户当天数据

## B. meta blob（tomatoState / todoState / settingsState / habitsState）

- [ ] blob 新形状已带 `schemaV` 字段并递增
- [ ] 读端使用 `raw.schemaV || 1` 宽松读取，旧数据（无版本字段）不报错
- [ ] 恢复/导入端拒绝 `schemaV` 高于当前版本的 blob（明确报错，不静默吞）
- [ ] 回滚场景自测：旧版读新版写出的备份 → 读端宽松降级，不崩溃、不写坏数据

## C. config.json

- [ ] 每个新键都进了 `DEFAULT` 的 spread——缺这步用户配置文件里没有该键时读到 undefined
- [ ] 键名无拼写不一致（DEFAULT 键与读写处完全一致）

## D. CLI 兼容

- [ ] CLI 与主进程共享同一个库文件：新表/新列/新 blob 形状在 CLI 侧可读（跑一次 CLI 冒烟），CLI 不假设列存在
- [ ] CLI 写入的数据主进程可读（双向形状兼容）

## E. 回滚 / 降级演练

- [ ] 用上一稳定版二进制打开本版数据：能启动、宽松兼容、带版本的数据被拒绝而非误读
- [ ] 备份文件由本版写 → 上一稳定版恢复：行为符合预期（拒绝或降级，二选一明确）

## F. 发布动作

- [ ] 以上全部勾完后才打 tag / 发 Release
- [ ] 若本次 schemaVersion 递增，在 Release 说明中注明「数据结构升级，建议先备份」
