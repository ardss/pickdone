# PickDone 付费云同步方案评估简报（自包含）

> 本文档面向没有任何上下文的评估者。目标：评估"从现有 LAN 同步架构演进到付费云同步"的整体思路是否成立、风险是否被正确识别、分期路线是否合理。

## 1. 项目背景

**产品**：PickDone（拾事），本地优先的桌面任务管理应用（Electron 39 + Vue 3 + CJS 主进程，Node 单进程，SQLite 本地库）。
**定位**：本地工作台，数据本地优先；品牌色松石青；开源思路参考 SiYuan（思源）模式 = 核心开源 + 托管同步收费。
**平台**：Windows / Linux（x64 + arm64），无移动端。典型用户设备数：2-4 台。
**商业化基线**：此前已定调"开源思源模式"——免费档数据永不删，付费点在同步托管。

## 2. 现状：已完成的 LAN 同步架构（近一个月真实开发+三机真机演练的产物）

### 2.1 数据与复制模型

- **本地 SQLite 为唯一事实源**，所有写入（渲染端、CLI）走单一写入管线（command bus，声明化 manifest，门外写入=0 有门禁证明）。
- **oplog 环**：变更日志为纯指针（entity / entityId / ts），内容在出口处按需水合（hydrateRow），避免日志膨胀。
- **LWW 合并**（last-write-wins，`shared/sync-core/merge.mjs`）：单文件、纯函数、有完整单元测试。
- **行溯源（protocol v3，刚落地）**：todos 表新增 `syncAuthor` 列 = 产生该行当前 updatedAt 的设备；跨跳保留（不随单跳 deviceId 覆写）。作用：区分"同一作者的陈旧回声"（不生成冲突副本）与"真正的他端冲突"（loser 物化进回收站，不丢数据）。未知作者保守处理。
- **水位机制**：每对 peer 维护独立推/拉水位，增量同步；断线重连后从水位续传。
- **快照协议**：新设备首同步拉全量快照，有 mutual-busy 门控。
- **冲突策略**：败者不删除，物化为冲突副本进回收站。
- **安全**：per-pair 配对密钥（AES-256-GCM 传输加密，每对设备独立 secret，配对时双向确认）；状态接口已 redact secret。

### 2.2 同步调度

- 触发式 round：定时心跳 + 变更触发 + 失败退避；批量写入；flush 有 stall 预算防饿死。
- 全部在 Electron 主进程内运行（无独立进程）。
- 曾有 hydration O(n²) 和饿死问题，已根治（分块推送/批量落盘/水位门控）。

### 2.3 验证程度（重要：评估者需知道可信度）

- **三台真机长期演练**：Windows 台式机 A、Windows 笔记本 B、ARM 板 lubancat C，星型拓扑（B、C 均只与 A 配对），跨 ~3 周多轮联调。
- 发现并修复的问题（节选，均有回归测试）：全局配对密钥导致旧配对失效（F1，已改 per-pair）、冲突双侧进回收站 C 版丢失（F2，已改行溯源）、推停滞、水位漂移、毒行、恢复时序、配对限流、种子迁移等。
- 单元测试 ~2600+ 全绿（含真实进程回环套件）；连续三轮全量扫描零新 P0/P1 后停止（有明确停止判据，写入 docs/sync-coverage-matrix.md）。
- **尚未验证**：公网/NAT 环境（目前全部演练在同一局域网）；移动弱网；长连接保活。

### 2.4 已知事实：拓扑实际已收敛为星型

尽管引擎支持网状 P2P，真机演练中实际操作收敛为星型（一台上经常开的设备充当事实枢纽，其他设备只与它配对）。多设备互连的冲突扇出、配对管理成本在实践中被星型规避。

## 3. 提议的方向：付费云同步

### 3.1 核心架构决策（待拍板）

**云端 = 现有"无头枢纽角色"部署到服务器 + 账号层。**即：
- 云服务器不是新的第二套同步系统，而是把同步引擎的"一个永远在线的 peer"搬上机房；
- 客户端连云端的方式复用现有 client dial 逻辑（IP 换域名）；
- 服务器存储 = 每账号一份 oplog（append-only + 定期快照），**服务器不做语义合并，LWW 逻辑保持在端上**。

### 3.2 必须先拍板的分叉：哑存储 vs 聪明服务器

| | 路线 A：哑存储+E2E（当前推荐） | 路线 B：聪明服务器 |
|---|---|---|
| 服务器角色 | 加密 blob 仓库+信箱，看不懂数据 | 拥有明文，做合并/查询 |
| 合并逻辑位置 | 端上（现成代码） | 需在云端实现第二份 |
| 隐私/合规 | 泄露也是密文，成本低 | 明文托管，个保法成本真实 |
| 高级功能（服务端搜索/AI） | 做不了（除非另开明示授权管道） | 容易 |
| 与品牌自洽度 | 高（本地优先） | 中 |

**当前倾向 A**；若未来做云端 AI，加"用户显式授权的可选明文管道"而非默认明文。

### 3.3 存储形态（每账号）

```
account/
  identity.json      # 账号 + 设备注册表
  oplog/             # 追加式变更日志，按 seq 分段（加密 ndjson）
  snapshot/          # 定期物化快照（新设备只拉最新快照+增量尾）
  attachments/       # 附件内容寻址 blob（去重）
```

复用现有：水位指针（增量）、快照协议（首同步）、per-pair secret（升级为 per-account secret + per-device key）。

### 3.4 账号与收费

- 注册：邮箱+密码；密码派生认证密钥上服务器，数据加密用独立数据密钥（不上服务器）；密码重置=数据密钥丢失，配恢复短语机制（参考 Bitwarden/Standard Notes）。
- **收费门控放在云端通道，不放客户端功能**：局域网同步永远全功能免费；云同步免费档做钩子（如 1 设备+100MB），付费档（多设备+容量+版本历史）做收入。
- 支付：初期用聚合支付平台（爱发电类），规避个体资质长周期。

### 3.5 分期路线

- **M0（1-2 天）**：定调文档，拍死 A/B 路线。
- **M1（约 1 周）**：无头枢纽模式先行——同一二进制加 `--sync-hub` 角色（无 GUI、只做 peer），部署到现有的 lubancat ARM 板当"私有云"。零服务器成本，先踩 NAT/弱网/保活/设备注册的坑；即使付费计划缩水，"可自建同步服务器"也独立成立为卖点。
- **M2（2-3 周）**：枢纽二进制服务化（去局域网发现依赖、加设备注册表），部署单实例公网，客户端加"云端 peer"配置。此阶段仍不收钱不开放注册。
- **M3（约 2 周）**：账号+计费壳（注册/设备管理/配额/支付），开放内测。
- **M4**：运营项（多实例、监控、备份、条款）。

### 3.6 已预判的坑（提案者自列）

1. 公网长连接保活：移动/公司网络掐空闲 TCP，心跳与重连退避需为公网重新调参。
2. 快照计费与频率控制：否则免费档配额被历史版本吃光。
3. E2E 恢复陷阱：忘密码+丢恢复短语=数据永久丢失，需在注册流程明示。
4. 服务器虽"只是信箱"，仍需处理：配额执行、滥用、设备数限制、oplog 段的垃圾回收（客户端拉完的旧段何时删）。

## 4. 提案者自我认知的开放问题（请评估者重点审）

1. **服务器不做语义合并是否正确**？oplog 里是内容指针+水合出口的设计是为局域网低延迟场景做的；公网高延迟下，客户端拉 oplog 再水合的首同步/大变更性能是否可接受？
2. **oplog 的服务器侧 GC**：如何知道所有活跃设备都拉到了某段？（现有水位是 per-peer 的，服务器需要聚合所有设备水位取最小值才能删段——孤儿设备/长期离线设备会阻塞 GC，如何处理？）
3. **免费档 1 设备的界定**：设备注册表的吊销/换机流程，是否会被滥用为无限设备？
4. **A 路线下账号迁移**：现有用户已有本地库+deviceId，接入云端的账号绑定与既有 LAN 配对并存策略未细化。
5. **单实例容量假设**（"几千账号"）未做任何压测，纯估算。
6. **商业侧完全未验证**：目标用户是否愿意为此付费、定价、与 TickTick 等免费云同步竞品的差异化说服力。

## 5. 评估请求

请就以下维度给出判断，并指出提案中未识别的风险：
1. 整体架构方向（云=枢纽角色上云、服务器哑存储、合并留在端上）是否是这类产品的正确选择？有没有被忽略的第三条路？
2. 分期路线的顺序与粒度是否合理？M1（私有枢纽先行）是否如提案者所说是最优第一步？
3. 第 4 节的开放问题中，哪些是方案级的（会推翻架构），哪些是实现级的？
4. 隐私与合规（中国大陆运营、E2E、聚合收款）方面有无提案者未意识到的硬约束？

## 6. 评审采纳记录（2026-09-29，内部评审后定稿）

外部评审结论：A 路线成立但需升级定义。采纳 7 项核心修正：

1. **架构定义修正**：云 = "协议感知但业务语义盲的 Sync Relay"，不是"永远在线的 LAN peer"。服务器懂 account/device/seq/ack/generation/snapshot/lease/GC，不懂业务字段。原"IP 换域名"表述废弃，公网 transport 需完整重定义（TLS/设备认证/连接生命周期/幂等/续传/代理兼容/睡眠唤醒）。
2. **GC 为协议级状态机**：设备生命周期（ACTIVE→STALE→DETACHED，含时限策略）+ durable ACK + snapshot generation + compaction boundary；服务器永久保留 current snapshot + 安全 oplog tail；废弃 min-watermark GC（会被长期离线设备卡死）。
3. **附件分轨**：metadata 同步与 blob 同步拆为两个子系统，允许 metadata 先行、blob 内容寻址后补、断点续传。
4. **版本历史由 snapshot retention 控制**，与 oplog 保存期解耦（Current/Daily/Weekly snapshot 分层）。
5. **设备槽位 + entitlement 服务端执行**：device slots + replacement allowance + 服务端保留 device/replacement history；门控不在客户端。
6. **身份模型**：Account → Device → {local identity, cloud identity, LAN peers}，四概念显式分离，禁止 deviceId==account 隐含假设；账号迁移提升为 M2 核心设计。
7. **大陆合规前置**：E2E 不豁免个保法（日志/IP/支付记录为个人信息）；日志系统第一天按 PII minimization 设计；注销删除机制提前定义；中国区优先部署；聚合支付视为 Payment Adapter（可替换），不视为资质豁免；ICP/增值电信资质在 M3 前做正式法律判断。

**路线修订**：M0.5（新增，2-3 天）= 《Cloud Sync Protocol v1》文档，定义死 10 个对象（Account/Device/Peer/Sequence/ACK/Snapshot Generation/Lease/GC/Recovery/Blob）+ 设备状态机 + GC 安全边界，禁止 LAN peer 概念隐式带入云端；M1 = Internet Transport Adapter + Lubancat 作为第一个 relay 实现（不做支付、不做账号）；M2/M3/M4 同原案。Hybrid Server（临时解密 worker）降级为一行"保留可能性"，不进里程碑。
